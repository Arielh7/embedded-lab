Bare-metal firmware that uses **Pin Change Interrupts (PCINT0/PCINT1)** on PB0 and PB1 to increment/decrement a counter displayed as a **3-bit binary value** on PD0–PD2. Demonstrates how PCINTs differ from external interrupts (INT0/INT1) — any logical change on the pin triggers the ISR, and the direction is determined by reading the pin state inside the handler. Part of my embedded firmware collection built with **PlatformIO**, simulated in **Proteus** (no physical hardware).

---

## ✨ Features

- ✅ Bare-metal C (no Arduino framework)
- ✅ **Pin Change Interrupts** on PB0 and PB1 (PCINT0/PCINT1)
- ✅ Both buttons share one ISR (`PCINT0_vect`), direction detected by pin state
- ✅ Counter range 0–7, output as **3-bit binary** on PD0–PD2
- ✅ Software debounce (20 ms re-check) inside the ISR
- ✅ Target: ATmega328P @ 8 MHz

## ⚙️ How it works

1.  **Pin setup:** `DDRD` sets PD0–PD2 as outputs (binary LEDs). `DDRB` configures PB0 and PB1 as inputs (buttons).
2.  **PCINT config:**
    - `PCICR |= (1 << PCIE0)` enables the **Pin Change Interrupt group 0** (PCINT0–PCINT7, i.e., all PORTB pins).
    - `PCMSK0 |= (PCINT0 | PCINT1)` unmasks only PB0 and PB1 — the rest of PORTB won't trigger the ISR.
    - `sei()` enables global interrupts.
3.  **ISR (`PCINT0_vect`):** fires on **any logical change** (rising or falling edge) on the enabled pins. The handler:
    - Checks if **PB0** caused the event → 20 ms debounce → increment (`counter < 7`).
    - Checks if **PB1** caused the event → 20 ms debounce → decrement (`counter > 0`).
    - Both branches can run in one call if both pins change simultaneously.
4.  **Main loop:** continuously writes `counter` to `PORTD`, lighting the 3 LEDs as a binary number (000 → 111).

### Why PCINT instead of INT0/INT1?

| Feature                   | INT0 / INT1                                 | PCINT0–PCINT23                      |
| ------------------------- | ------------------------------------------- | ----------------------------------- |
| Trigger                   | Configurable edge (rising / falling / both) | **Any logical change** only         |
| Granularity               | Per-pin                                     | **Per-group** (shared vector)       |
| Pins                      | Fixed (PD2, PD3)                            | Any pin (grouped by port)           |
| ISR must decide direction | No                                          | **Yes** — read pin state inside ISR |

That's why the ISR checks `PINB & (1 << PINB0)` and `PINB & (1 << PINB1)` — the vector doesn't tell you _which_ pin changed or in _which_ direction, so you must read the current state.

| -------- | ------------------ | ---------------------------- |

| `PCMSK0` | `PCINT0 \| PCINT1` | Unmask PB0 and PB1 only      |
| `SREG.I` | set via `sei()`    | Global interrupt enable      |

## 🚀 Build and simulate

```bash
pio run          # Generates the .hex
```

`platformio.ini`:

```ini
[env:ATmega328P]
platform = atmelavr
board = ATmega328P
framework = arduino
board_build.f_cpu = 8000000L
```

1.  Open the `.pdsprj` file in Proteus.
2.  Double-click the MCU and set **Clock Frequency** to 8 MHz (must match `F_CPU`).
3.  Load the `.hex` generated by PlatformIO into program memory.
4.  Run the simulation — press B0 to increment, B1 to decrement, watch the 3 LEDs.

## 📝 Notes & limitations

- **ISR fires on both edges** (rising _and_ falling) because PCINT has no edge selection. On real hardware this means one press can trigger the ISR twice (on press and on release). The debounce plus the `PINB` check filters release events (pin is low then), but the ISR still runs twice per press — harmless here, wasteful in general.
- **`_delay_ms(20)` inside the ISR** blocks other interrupts for 20 ms. Bad practice in production code; a timer-based debounce or a flag-checked-in-main approach would be better.
- **Both buttons share `PCINT0_vect`** — the handler checks both pins every call. Fine for 2 buttons; for many pins, a `changed = PINB ^ lastPINB` pattern is cleaner.
- **Proteus has ideal switches** (no bounce), so the debounce isn't observable in simulation.
- **Counter starts at 7** (`volatile uint8_t counter = 7;`) — all 3 LEDs on at boot. Change to `0` if you want them off initially.
- Troubleshooting quick-ref:
  - Counter never changes → check `PCICR`/`PCMSK0` and that `sei()` is called.
  - Counter changes on release too → expected with PCINT; the `PINB` check should filter it, verify pull-downs are present.
  - Counter jumps by more than 1 → debounce too short or missing pull-down (floating input).
  - Wrong LEDs lit → verify PD0–PD2 wiring and bit order.
- **Future improvements:** 4-bit output to a 7-segment display or LCD, up/down via INT0/INT1 instead of PCINT, long-press detection, auto-repeat.
