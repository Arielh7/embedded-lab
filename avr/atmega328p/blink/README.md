Bare-metal firmware that blinks a **single LED on PD0** of an ATmega328P every 1000 ms. The simplest possible "hello world" for AVR: configure a pin as output, toggle it, and wait. Part of my embedded firmware collection built with **PlatformIO**, simulated in **Proteus** (no physical hardware).

---

## ✨ Features

- ✅ Bare-metal C (no Arduino framework)
- ✅ Direct register manipulation (`DDRD`, `PORTD`)
- ✅ `_delay_ms()` for timing
- ✅ Minimal project — good starting point for the workflow
- ✅ Target: ATmega328P @ 8 MHz

---

## 🛠️ Hardware (simulated in Proteus)

| Component | Detail                                       |
| --------- | -------------------------------------------- |
| MCU       | ATmega328P                                   |
| Clock     | 8 MHz (see `platformio.ini`)                 |
| Pin used  | PD0 (pin 2 on DIP package)                   |
| LED       | 1x, with 220 Ω series resistor               |
| Reset     | 10 kΩ pull-up between RESET (pin 1) and +5 V |

> ⚠️ **Proteus simulation only.** Not tested on physical hardware.

## ⚙️ How it works

1.  **Pin setup:** `DDRD |= (1 << 0)` configures PD0 as an output.
2.  **Loop:** inside `while(1)`, `PORTD |= (1 << 0)` drives PD0 high (LED on), waits 1000 ms with `_delay_ms(1000)`, then `PORTD &= ~(1 << 0)` drives it low (LED off) and waits another 1000 ms.
3.  **Full cycle:** 1000 ms on + 1000 ms off = **2 s period** (0.5 Hz blink rate).

The `_delay_ms()` function relies on `F_CPU`, which is set to `8000000L` in `platformio.ini`. If `F_CPU` doesn't match the MCU clock in Proteus, the timing will be off.

## 🚀 Build and simulate

```bash
pio run          # Generates the .hex
```

`platformio.ini`:

```ini
[env:ATmega328P]
platform = atmelavr
board = ATmega328P
framework = arduino
board_build.f_cpu = 8000000L
```

1.  Open the `.pdsprj` file in Proteus.
2.  Double-click the MCU and set **Clock Frequency** to 8 MHz (must match `F_CPU`).
3.  Load the `.hex` generated by PlatformIO into program memory.
4.  Run the simulation — the LED should toggle once per second.

---

## 📝 Notes & limitations

- **Blocking delays:** `_delay_ms()` busy-waits, so nothing else can run during the delay. Fine for a blink, but a Timer-based approach would scale to real projects.
- **`F_CPU` must match** both the compiler define and the Proteus clock, or `_delay_ms()` timing will be wrong.
- `return 0;` after `while(1)` is unreachable — harmless, but some compilers warn about it.
- **Future improvements:** blink with Timer0/Timer1 instead of `_delay_ms()`, pattern sequences (SOS, breathing with PWM), multiple LEDs.
